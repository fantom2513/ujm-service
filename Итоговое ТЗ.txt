ТЕХНИЧЕСКОЕ ЗАДАНИЕ
Copilot для построения Mermaid-схем

Версия: итоговая рабочая редакция
Примечание: документ объединяет правки из редактируемого поля и последние уточнения по ошибкам и восстановлению состояния после обновления страницы.


1. ЦЕЛЬ СЕРВИСА

Создать рабочий веб-сервис, который получает техническое задание пользователя, анализирует его с помощью ИИ и строит визуальную Mermaid-схему в заранее определённом формате.

После построения пользователь может:

- просмотреть схему;
- приблизить или отдалить схему;
- перемещать схему внутри области просмотра;
- изменить схему с помощью AI-чата;
- скачать схему в PNG, SVG или PDF;
- создать новую схему;
- перейти на главную страницу, где собраны все сервисы Copilot.

Интерфейс должен соответствовать предоставленным Figma-макетам и состояниям компонентов.


2. ЧТО НЕ ВХОДИТ В СЕРВИС

Не реализовывать:

- регистрацию;
- авторизацию;
- личный кабинет;
- создание проектов;
- список проектов;
- сохранение истории проектов;
- сохранение истории версий схемы;
- постоянную базу данных для пользовательских данных;
- основную страницу продукта, на которой размещён виджет Copilot.

Данные существуют только в рамках текущей вкладки и текущей пользовательской сессии.

Для восстановления страницы после обновления допускается временное хранение состояния в браузере в пределах текущей вкладки, например sessionStorage.

После обновления страницы должны восстанавливаться, если они уже были получены или введены:

- построенная схема;
- текущая переписка с Copilot;
- исходный контекст задачи;
- введённая ссылка;
- дополнительные детали;
- выбранный тип источника;
- состояние страницы результата;
- текущий масштаб и положение схемы.

Ограничение браузера: после полного обновления страницы нельзя автоматически восстановить доступ к локальному файлу пользователя, если файл ещё не был отправлен и обработан. В таком случае пользователь должен прикрепить файл повторно.

Данные очищаются после:

- подтверждения действия «Новая схема»;
- подтверждения перехода «На главную»;
- закрытия текущей вкладки браузера.

Постоянное хранение данных и база данных не требуются.


3. СТРАНИЦЫ СЕРВИСА

Необходимо реализовать две страницы.

3.1. Стартовая страница

Страница, на которой пользователь выбирает источник технического задания и запускает построение схемы.

3.2. Страница результата

Страница, на которой отображаются:

- построенная схема;
- AI-чат;
- исходное ТЗ;
- дополнительные детали;
- действия со схемой;
- навигационные кнопки.

Основную страницу продукта создавать не нужно. Необходимо только предусмотреть переход на неё по заранее заданному адресу.


4. СТАРТОВАЯ СТРАНИЦА

4.1. Источники технического задания

Пользователь выбирает только один источник.

Доступны три варианта:

1. Текстовый файл.
2. Запись встречи.
3. Ссылка на Jira или Confluence.

По умолчанию выбран вариант «Текстовый файл».

При переключении на другой источник данные предыдущего источника очищаются.


4.2. Текстовый файл

Поддерживаемые форматы:

- TXT;
- DOCX;
- PDF.

PDF поддерживается только в том случае, если из него можно извлечь текст.

Сканированные PDF, состоящие из изображений и не содержащие доступного текста, не распознаются. Распознавание текста на изображениях не реализовывать.

Если выбран такой PDF, файл не должен успешно загружаться и обрабатываться. Отдельную пользовательскую ошибку или отдельный экран не создавать. Использовать существующее состояние неуспешной загрузки файла в компоненте attachment.

Максимальный размер файла — 10 МБ.

Пользователь может загрузить только один файл.

Система должна проверять:

- прикреплён ли файл;
- поддерживается ли формат;
- не превышает ли файл допустимый размер;
- может ли система обработать содержимое файла;
- соответствует ли фактический тип файла заявленному формату.

В интерфейсе предусмотрены только следующие пользовательские ошибки.

Ошибка 1. Файл не прикреплён

Текст:
«Необходимо прикрепить файл»

Ошибка появляется, если пользователь нажимает «Построить схему», не прикрепив файл.

Ошибка 2. Некорректный формат файла

Текст:
«Некорректный формат файла»

Эта ошибка используется, если:

- формат файла не поддерживается;
- файл повреждён;
- содержимое файла невозможно прочитать;
- из файла невозможно извлечь данные для анализа.

Для сканированных PDF без доступного текста использовать существующее состояние неуспешной загрузки в компоненте attachment.

Технические причины могут различаться на backend, но пользователю показывается одно утверждённое состояние из Figma.

Ошибка 3. Превышен размер файла

Текст:
«Файл превышает 10 МБ»

Ошибка появляется сразу после выбора слишком большого файла.

Ошибка загрузки attachment

Если передача файла на сервер прервалась, использовать состояние ошибки, предусмотренное в компоненте attachment.

Для этой ошибки не создавать отдельный экран, если она уже полностью описана состояниями компонента.


4.3. Запись встречи

Поддерживаемые форматы:

- MP3;
- M4A;
- MP4;
- WebM.

Максимальный размер файла — 100 МБ.

Пользователь может загрузить только одну запись.

Для MP4 и WebM backend должен извлечь аудиодорожку.

После загрузки backend выполняет транскрибацию записи и использует полученный текст для построения схемы.

Система должна проверять:

- прикреплена ли запись;
- поддерживается ли формат;
- не превышает ли файл допустимый размер;
- соответствует ли фактический тип файла заявленному формату;
- может ли система обработать и расшифровать запись;
- есть ли пригодная для обработки аудиодорожка.

В интерфейсе предусмотрены только следующие пользовательские ошибки.

Ошибка 1. Запись не прикреплена

Текст:
«Необходимо прикрепить файл»

Ошибка появляется, если пользователь нажимает «Построить схему», не прикрепив запись.

Ошибка 2. Некорректный формат файла

Текст:
«Некорректный формат файла»

Эта ошибка используется, если:

- формат файла не поддерживается;
- файл повреждён;
- в видео отсутствует пригодная для обработки аудиодорожка;
- запись невозможно расшифровать;
- в записи невозможно распознать содержимое для построения схемы.

Технические причины могут различаться на backend, но пользователю показывается одно утверждённое состояние из Figma.

Ошибка 3. Превышен размер файла

Текст:
«Файл превышает 100 МБ»

Ошибка появляется сразу после выбора слишком большого файла.

Ошибка загрузки attachment

Если передача записи на сервер прервалась, использовать состояние ошибки, предусмотренное в компоненте attachment.

Для этой ошибки не создавать отдельный экран.


4.4. Ссылка на Jira или Confluence

Пользователь может добавить ссылку на:

- Jira;
- Confluence.

Пользователь вставляет ссылку в отдельное текстовое поле.

Backend должен:

1. Проверить ссылку.
2. Определить, ведёт ли она на Jira или Confluence.
3. Получить доступное содержимое.
4. Преобразовать содержимое в текст.
5. Передать полученные данные в общий AI-пайплайн.

Не запрашивать у пользователя логин, пароль или API-токен.

Доступ к закрытым корпоративным страницам должен выполняться через заранее настроенные серверные данные доступа.

В интерфейсе предусмотрены только следующие ошибки.

Ошибка 1. Поле не заполнено

Текст:
«Поле обязательно для заполнения»

Ошибка появляется, если пользователь нажимает «Построить схему» с пустым полем.

Ошибка 2. Неверный формат ссылки

Текст:
«Неверный формат ссылки»

Ошибка используется, если:

- введён некорректный URL;
- ссылка ведёт не на Jira или Confluence;
- структура ссылки не поддерживается сервисом.

Ошибка 3. Источник недоступен

Текст:
«Источник недоступен. Проверьте ссылку и права доступа»

Ошибка используется, если:

- страница не найдена;
- у сервиса нет доступа;
- Jira или Confluence временно недоступны;
- содержимое страницы невозможно получить;
- из страницы невозможно извлечь данные для анализа.

Отдельную пользовательскую ошибку «На странице нет подходящего содержимого» не создавать.

Если источник удалось прочитать, полученные данные передаются в AI в любом доступном объёме. При неполном описании AI должен учитывать дополнительные детали пользователя и правила системного промпта.


4.5. Дополнительные детали

На стартовой странице находится необязательное текстовое поле.

Пользователь может указать дополнительные требования, например:

- построить схему только для руководителя;
- добавить роли, отсутствующие в ТЗ;
- исключить технические процессы;
- показать только основной сценарий;
- добавить дополнительное бизнес-условие;
- сделать схему более или менее подробной.

Дополнительные детали должны передаваться модели отдельно от исходного ТЗ.

ИИ должен понимать, где находится исходное ТЗ, а где — дополнительная инструкция пользователя.


4.6. Основная кнопка

Текст кнопки:
«Построить схему»

Кнопка отправляет данные на следующий этап после добавления корректного источника. Если источник не добавлен или не прошёл проверку, показывается соответствующая ошибка из Figma.

После нажатия:

- повторное нажатие блокируется;
- внутри кнопки показывается загрузка;
- источник и дополнительные детали временно нельзя изменять;
- отдельная страница статуса не открывается.

Загрузка отображается на той же стартовой странице.

Для каждого источника предусмотрен отдельный макет loading-состояния:

- текстовый файл;
- запись встречи;
- ссылка.


5. ОБРАБОТКА ДАННЫХ

5.1. Текстовый файл

Загрузка файла
→ проверка
→ извлечение текста
→ подготовка текста
→ AI-генерация
→ проверка Mermaid
→ страница результата

Для PDF извлечение текста выполняется только при наличии текстового слоя. Сканированные PDF без доступного текста не распознаются и не передаются в AI-пайплайн.

5.2. Запись встречи

Загрузка записи
→ проверка
→ извлечение аудио при необходимости
→ транскрибация
→ подготовка текста
→ AI-генерация
→ проверка Mermaid
→ страница результата

5.3. Jira или Confluence

Проверка ссылки
→ получение содержимого
→ подготовка текста
→ AI-генерация
→ проверка Mermaid
→ страница результата


6. ГЕНЕРАЦИЯ MERMAID-СХЕМЫ

На backend должен храниться отдельный системный промпт, который определяет:

- формат схемы;
- правила оформления;
- структуру;
- допустимые Mermaid-конструкции;
- отображение ролей;
- правила ветвлений;
- поведение при неполном ТЗ.

Промпт не должен передаваться на frontend или быть виден пользователю.

Утверждённый промпт первоначальной генерации требует, чтобы ИИ возвращал только Mermaid-код.

Backend должен получить от ИИ полный Mermaid-код. Если frontend требуется служебное название схемы или внутренние предупреждения, backend формирует их отдельно без изменения утверждённого промпта и без показа пользователю.

Перед отображением backend должен проверить Mermaid-код.

Если Mermaid-код содержит ошибку:

1. Выполнить одну автоматическую попытку исправления.
2. Повторно проверить код.
3. Если исправление не помогло, показать общую ошибку построения.

Общая ошибка генерации одинакова для всех источников.

Название макета:
Start / Diagram generation / Error
https://www.figma.com/design/QYHPAe62MvCmHNQ0E8ET82/Untitled?node-id=845-23430&t=frWepVig5iEIuq7E-4

Текст:
«Схема не сформирована. Перезагрузите страницу или повторите попытку позже»

При появлении ошибки:

- состояние загрузки завершается;
- кнопка «Построить схему» снова становится доступной;
- выбранный источник не удаляется;
- дополнительные детали не очищаются;
- пользователь может повторно нажать «Построить схему»;
- при обновлении страницы заполненные данные стартовой страницы должны восстановиться, кроме локального файла, если браузер не позволяет восстановить к нему доступ.

Технические подробности ошибки, Mermaid-код, stack trace и названия внутренних моделей пользователю не показываются.


7. СТРАНИЦА РЕЗУЛЬТАТА

На странице результата отображаются:

- визуальная схема;
- AI-чат;
- исходный источник в чате;
- дополнительные детали, если они были добавлены;
- кнопка «На главную»;
- кнопка «Новая схема»;
- кнопка «Скачать схему».

Mermaid-код не отображается как отдельный редактор.

Редактор Mermaid-кода не нужен.


8. ОТОБРАЖЕНИЕ ИСХОДНОГО ТЗ В ЧАТЕ

Исходное ТЗ дублируется в области чата.

Оно отображается как отдельный блок контекста, а не как обычное сообщение пользователя.

8.1. Для текстового файла

Показывать attachment:

- название файла;
- формат;
- размер.

Содержимое документа в чат не выводить.

8.2. Для записи

Показывать attachment:

- название записи;
- формат;
- размер.

Транскрибацию не показывать.

8.3. Для ссылки

Показывать:

- Jira или Confluence;
- адрес или сокращённый адрес;
- название задачи или страницы, если оно доступно.

8.4. Дополнительные детали

Если пользователь вводил дополнительные детали, показать их отдельным блоком контекста.


9. ПРОСМОТР СХЕМЫ

Схему необходимо отображать в отдельной области страницы результата.

Предусмотрены состояния:

- обычный масштаб;
- схема приближена;
- схема отдалена.

Управление масштабом:

- колесо мыши над областью схемы;
- кнопка «+»;
- кнопка «−»;
- шаг изменения масштаба через кнопки — 25%.

Схему можно перемещать мышью внутри области просмотра.

После первоначального построения схема должна автоматически центрироваться.

Полноэкранный режим не нужен.

Названия макетов:

- Result / Page / Default
- Result / Diagram / Zoomed in

Параметры масштаба:

- минимальный масштаб — 25%;
- максимальный масштаб — 200%;
- шаг изменения масштаба кнопками «+» и «−» — 25%.


10. AI-ЧАТ

Чат используется для изменения уже построенной схемы.

Предустановленные запросы показаны в чате кнопками. При нажатии на кнопку чат запускает перегенерацию в соответствии с запросом:

- «Разбить схему на смысловые блоки»;
- «Упростить схему»;
- «Выделить основной путь».

При отправке сообщения backend получает:

- исходное нормализованное ТЗ;
- дополнительные детали;
- текущий Mermaid-код;
- сообщение пользователя;
- данные прикреплённого файла, если пользователь добавил файл к сообщению;
- системный промпт редактирования.

ИИ должен вернуть:

- полный обновлённый Mermaid-код;
- текстовый ответ для чата.

После получения ответа:

1. Проверить ответ.
2. Проверить Mermaid-код.
3. Обновить схему только после успешной проверки.
4. При ошибке оставить текущую схему без изменений.

Одновременно может выполняться только один AI-запрос.

Во время ответа повторная отправка должна быть недоступна.

Состояния чата в макетах:

- Result / Chat / Initial
- Result / Chat / Task open
- Result / Chat / User message
- Result / Chat / Generating
- Result / Chat / Generating by button
- Result / Chat / AI response
- Result / Chat / Error

Дополнительная функциональность чата:

- прикрепление файла через кнопку в текстовом поле;
- при нажатии открывается проводник на устройстве пользователя;
- пользователь может прикрепить к сообщению только один файл;
- прикреплённый файл можно удалить при наведении и клике на действие удаления;
- пользователь может оценить ответ Copilot;
- пользователь может скопировать ответ Copilot;
- если в ответе по макету отображается ссылка на Mermaid-код, при копировании ответа ссылка также копируется;
- старые сообщения редактировать нельзя;
- отдельной кнопки повтора запроса нет;
- отдельная кнопка остановки генерации пока не предусмотрена;
- отмена последнего изменения выполняется текстовым запросом, например: «Верни к предыдущему ответу».

Файл в AI-чате необязателен.

Максимальный размер прикреплённого файла — 10 МБ.

Поддерживаемые текстовые и табличные форматы:

- TXT;
- DOCX;
- PDF;
- XLS;
- XLSX;
- CSV.

Поддерживаемые форматы записей:

- MP3;
- M4A;
- MP4;
- WebM.

Изображения не поддерживаются.

Для PDF действуют общие правила: принимаются только PDF с доступным текстом. Сканированные PDF не распознаются.

Текстовый или табличный файл используется как дополнительный контекст для текущего запроса.

Аудиозапись или видео должны быть расшифрованы. Полученная транскрибация используется как дополнительный контекст для текущего запроса.

Прикреплённый файл:

- не заменяет первоначальное ТЗ;
- не становится новым основным источником;
- обрабатывается вместе с текстом сообщения;
- временно хранится только во время обработки;
- удаляется после успешной обработки или ошибки.

Пользователь может удалить файл до отправки сообщения.

Для файла в чате используются существующие состояния attachment-компонента:

- некорректный формат;
- превышение размера 10 МБ;
- ошибка загрузки.

Не создавать отдельные экраны ошибок для файла в чате.

Не использовать ошибку «Необходимо прикрепить файл», потому что файл в сообщении чата необязателен.

Поведение поля во время генерации:

- пользователь не может отправить второй запрос;
- кнопка отправки недоступна;
- поле может оставаться доступным для набора текста, но отправка блокируется до завершения текущего ответа;
- прикрепление нового файла во время генерации блокируется;
- удаление прикреплённого файла во время генерации блокируется.

Точный формат текстового ответа Copilot:

- кратко подтвердить выполненное изменение;
- при необходимости перечислить, что изменилось;
- не выводить технические ошибки;
- не выводить полный Mermaid-код обычным текстом, если это не предусмотрено макетом.


11. СКАЧИВАНИЕ СХЕМЫ

На странице результата находится кнопка:
«Скачать схему»

При нажатии или наведении, согласно макету, открывается dropdown.

Варианты скачивания:

- PNG;
- SVG;
- PDF.

Mermaid-код через этот dropdown не скачивается.

Dropdown должен:

- закрываться после выбора формата;
- закрываться при клике вне элемента;
- закрываться по Escape;
- показывать состояние подготовки файла;
- показывать системную ошибку, если скачать файл не удалось.

Состояния:

- Result / Download / Dropdown open
- Result / Download / Exporting
- Result / Download / Error

11.1. PNG

Экспортировать только схему, без элементов интерфейса.

PNG должен:

- иметь хорошее разрешение;
- не быть размытым;
- не обрезать схему;
- иметь отступы;
- корректно работать с большими схемами;
- иметь белый фон.

11.2. SVG

SVG должен:

- содержать всю схему;
- иметь корректный viewBox;
- не обрезать узлы;
- сохранять качество при масштабировании;
- не содержать исполняемых скриптов;
- иметь прозрачный фон.

11.3. PDF

PDF должен:

- содержать только схему;
- не обрезать содержимое;
- сохранять читаемость текста;
- учитывать большие и широкие схемы;
- автоматически выбирать книжную или альбомную ориентацию в зависимости от пропорций схемы;
- использовать подходящий размер страницы или масштабирование с полями.

Название схемы в экспортируемый файл визуально не добавляется.

Имя скачиваемого файла:

- ux_arch_YYYY-MM-DD_HH-mm.png
- ux_arch_YYYY-MM-DD_HH-mm.svg
- ux_arch_YYYY-MM-DD_HH-mm.pdf


12. КНОПКА «НОВАЯ СХЕМА»

При нажатии открывается модальное окно.

Макет:
Result / Modal=New diagram / Open

Модальное окно предупреждает, что:

- схема не сохранится;
- переписка не сохранится;
- исходный файл или ссылка будут удалены;
- восстановить результат будет невозможно.

При отмене пользователь остаётся на странице результата.

При подтверждении:

1. Очищаются данные текущей сессии.
2. Удаляется текущая схема.
3. Удаляется чат.
4. Удаляется временное состояние браузера.
5. Пользователь возвращается на стартовую страницу Copilot.


13. КНОПКА «НА ГЛАВНУЮ»

При нажатии открывается отдельное модальное окно.

Макет:
Result / Modal=Go home / Open

Модальное окно предупреждает, что данные и схема не сохранятся.

При отмене пользователь остаётся на странице результата.

При подтверждении:

1. Очищается текущее состояние.
2. Удаляется временное состояние браузера.
3. Пользователь переходит на основную страницу продукта.

Основную страницу продукта создавать не нужно.

Адрес главной страницы должен задаваться отдельно и не быть жёстко прописан в коде.


14. НАВИГАЦИЯ, ОБНОВЛЕНИЕ И ПОТЕРЯ ДАННЫХ

Обновление страницы не должно приводить к потере уже построенной схемы и текущего состояния страницы.

На стартовой странице после обновления должны сохраняться:

- выбранный тип источника;
- введённая ссылка;
- дополнительные детали;
- информация о выбранном файле, если технически возможно восстановить её без повторного доступа к локальному файлу пользователя.

На странице результата после обновления должны восстанавливаться:

- схема;
- текущий чат;
- исходный контекст;
- дополнительные детали;
- текущий масштаб и положение схемы.

Модальные окна предупреждения использовать только при действиях, которые очищают текущую сессию и представлены в Figma:

- «Новая схема»;
- «На главную».

Для внутренних переходов использовать модальные окна из Figma.

Не использовать системные предупреждения браузера при обновлении страницы, закрытии вкладки и использовании браузерной кнопки «Назад».

При обновлении страницы результат и текущее состояние должны восстанавливаться автоматически, насколько это возможно технически.

При закрытии вкладки данные текущей сессии удаляются без предупреждения.

При использовании браузерной кнопки «Назад» текущее состояние не удаляется.


15. ПОЛЬЗОВАТЕЛЬСКИЕ ОШИБКИ

Реализовать только состояния ошибок, представленные в Figma-макетах.

15.1. Текстовый файл

Названия макетов:

- Start / Source=Text file / Error=File required
- Start / Source=Text file / Error=File format
- Start / Source=Text file / Error=File size

Тексты:

- «Необходимо прикрепить файл»;
- «Некорректный формат файла»;
- «Файл превышает 10 МБ».

Ошибка передачи файла отображается внутри компонента attachment.

15.2. Запись встречи

Названия макетов:

- Start / Source=Meeting recording / Error=File required
- Start / Source=Meeting recording / Error=File format
- Start / Source=Meeting recording / Error=File size

Тексты:

- «Необходимо прикрепить файл»;
- «Некорректный формат файла»;
- «Файл превышает 100 МБ».

Ошибка передачи записи отображается внутри компонента attachment.

15.3. Jira или Confluence

Названия макетов:

- Start / Source=Link / Error=Link required
- Start / Source=Link / Error=Invalid link
- Start / Source=Link / Error=Source unavailable

Тексты:

- «Поле обязательно для заполнения»;
- «Неверный формат ссылки»;
- «Источник недоступен. Проверьте ссылку и права доступа».

15.4. Общая ошибка формирования схемы

Название макета:
Start / Diagram generation / Error

Текст:
«Схема не сформирована. Перезагрузите страницу или повторите попытку позже»

15.5. Файл в AI-чате

Для файла, прикреплённого к сообщению AI-чата, использовать только существующие состояния attachment-компонента:

- некорректный формат;
- превышение размера 10 МБ;
- ошибка загрузки.

Не использовать ошибку «Необходимо прикрепить файл», потому что файл в сообщении чата необязателен.

Не добавлять дополнительные пользовательские ошибки, отсутствующие в Figma.

Внутренние технические ошибки должны сопоставляться с ближайшим подходящим пользовательским состоянием.


16. ХРАНЕНИЕ ДАННЫХ

Не использовать постоянное хранение пользовательских данных.

Загруженный файл должен:

1. Временно приниматься backend.
2. Проверяться.
3. Обрабатываться.
4. Удаляться после успешной обработки.
5. Удаляться при ошибке.

Для восстановления состояния после обновления страницы допускается временное хранение в браузере в пределах текущей вкладки:

- Mermaid-кода;
- визуального состояния схемы;
- сообщений чата;
- метаданных источника;
- дополнительных деталей;
- введённой ссылки;
- выбранного типа источника;
- масштаба и положения схемы.

Не сохранять на сервере постоянно:

- исходные файлы;
- транскрипты;
- файлы, прикреплённые к сообщениям AI-чата;
- пользовательские сообщения;
- Mermaid-код;
- историю схем.

Не выводить полное ТЗ и транскрипты в production-логи.


17. БЕЗОПАСНОСТЬ

Необходимо:

- хранить API-ключи только на backend;
- хранить системные промпты только на backend;
- не включать секреты в клиентский код;
- проверять размер файла на frontend и backend;
- проверять расширение и фактический тип файла;
- очищать названия файлов;
- исключить опасные пути и исполняемые файлы;
- ограничить время обработки;
- проверять Mermaid перед рендерингом;
- использовать безопасный режим Mermaid;
- очищать SVG;
- не рендерить пользовательский HTML;
- не показывать пользователю технические ошибки и stack trace.


18. ДИЗАЙН И FIGMA

Интерфейс должен соответствовать предоставленным Figma-макетам.

Figma содержит:

- стартовую страницу;
- варианты трёх источников;
- состояния загрузки;
- состояния ошибок;
- страницу результата;
- состояния масштаба схемы;
- состояния чата;
- dropdown скачивания;
- модальные окна;
- компоненты и их состояния.

Использовать названия фреймов по формуле:

Страница / Область / Состояние

Примеры:

- Start / Initial / Source=Text file / Empty
- Start / Source=Meeting recording / Loading
- Start / Diagram generation / Error
- Result / Page / Default
- Result / Diagram / Zoomed in
- Result / Chat / Generating
- Result / Download / Dropdown open
- Result / Modal=New diagram / Open

Не создавать визуальные состояния, которых нет в макетах или требованиях, без явного указания принятого решения.


19. ПЕРЕДАЧА РАЗРАБОТЧИКАМ

Результат должен быть самостоятельным переносимым проектом.

Проект должно быть возможно:

- передать архивом;
- разместить в корпоративном Git;
- запустить на другом компьютере;
- встроить в существующий продукт.

Не привязывать проект:

- к конкретному компьютеру;
- к локальному пути;
- к Codex;
- к личным аккаунтам;
- к реальным API-ключам.

Необходимо подготовить:

- исходный код;
- README с инструкцией запуска;
- список необходимых настроек;
- пример файла переменных окружения без секретов;
- описание подключения OpenAI;
- описание Jira и Confluence;
- описание обработки записей;
- описание системных промптов;
- список известных ограничений.


20. ЧТО ЕЩЁ НУЖНО ПОДТВЕРДИТЬ ИЛИ ДОПОЛНИТЬ

Перед окончательной передачей Codex нужно подтвердить или дополнить:

1. Точную схему доступа к Jira и Confluence.
2. Промпт редактирования Mermaid через чат.
3. Максимальную продолжительность записи.
4. Ограничения текстовых полей.
5. Требования к мобильной или адаптивной версии.
6. Модели OpenAI, лимиты и таймауты для генерации, редактирования и транскрибации.
