MERMAID VALIDATION AND CHAT UPDATE PIPELINE

Назначение:
Проверять результат генерации и редактирования до атомарного обновления схемы и сообщения в интерфейсе.

ВАЖНО:
- LLM не является единственным валидатором.
- Backend сначала выполняет детерминированные проверки.
- repairMermaid.prompt.txt вызывается максимум один раз.
- Невалидный результат никогда не заменяет текущую схему.
- В историю состояния попадают только полностью проверенные Mermaid-версии.

1. КОНТРАКТ ЗАПРОСА РЕДАКТИРОВАНИЯ

Backend формирует:
- sourceSpecification;
- additionalDetails;
- currentMermaid;
- previousMermaid, если есть;
- actionType;
- userMessage;
- attachmentContext, если есть;
- requestId;
- sessionId текущей вкладки.

Допустимые actionType:
- GROUP_SEMANTIC_BLOCKS;
- SIMPLIFY;
- HIGHLIGHT_MAIN_PATH;
- FREEFORM;
- RESTORE_PREVIOUS.

Быстрые действия всегда передают явный actionType.
Обычное текстовое сообщение передаёт FREEFORM, кроме распознанных команд восстановления.

2. РАСПОЗНАВАНИЕ ВОССТАНОВЛЕНИЯ

До обращения к LLM нормализовать USER_MESSAGE:
- trim;
- lowercase;
- заменить `ё` на `е`;
- убрать повторные пробелы и завершающую пунктуацию.

Фразы с явным смыслом отмены последнего изменения должны переводиться в RESTORE_PREVIOUS, например:
- «верни предыдущую версию»;
- «вернуть предыдущую версию»;
- «верни прошлую схему»;
- «отмени последнее изменение»;
- «откатить последнее изменение»;
- «назад к предыдущей схеме».

RESTORE_PREVIOUS желательно выполнять детерминированно без вызова LLM:
- если previousMermaid есть и валиден, вернуть его как новый currentMermaid;
- показать message «Предыдущая версия схемы восстановлена»;
- поменять местами currentMermaid и previousMermaid, чтобы повторная команда могла вернуть отменённую версию;
- если previousMermaid отсутствует, оставить currentMermaid и показать message «Предыдущая версия схемы недоступна».

Prompt поддерживает RESTORE_PREVIOUS как резервный путь, но основной backend-путь не должен зависеть от интерпретации модели.

3. СОСТОЯНИЕ ВЕРСИЙ

Хранить в рамках текущей вкладки:
- currentMermaid;
- previousMermaid;
- currentMessage или историю сообщений чата;
- activeRequestId.

Допустимо хранение в sessionStorage или существующем session-state проекта.
Постоянная база данных и отдельный UI истории не требуются.

Перед применением новой валидной схемы:
1. previousMermaid = currentMermaid;
2. currentMermaid = validatedMermaid;
3. добавить validated message в чат.

При ошибке:
- currentMermaid не менять;
- previousMermaid не менять;
- не добавлять невалидную версию в состояние.

4. ВЛОЖЕНИЕ В ЧАТЕ

Разрешено одно вложение на сообщение размером до 10 МБ.

Использовать существующий в проекте список поддерживаемых текстовых, табличных, аудио- и видеоформатов как единый источник истины.

Требования:
- изображения не поддерживать;
- PDF принимать только с текстовым слоем;
- OCR не выполнять;
- бинарный файл не передавать в системный промпт;
- до AI-запроса извлечь текст, таблицу или транскрибацию;
- передать модели только безопасный ATTACHMENT_CONTEXT;
- ограничить размер извлечённого контекста согласно конфигурации модели;
- при ошибке извлечения не запускать редактирование и не менять схему;
- показать понятное сообщение об ошибке вложения;
- имя, тип и размер файла можно показывать в UI;
- во время активного AI-запроса новое вложение недоступно.

Вложение является дополнительным контекстом USER_MESSAGE, а не заменой исходного ТЗ.

5. ПРОВЕРКА ОТВЕТА МОДЕЛИ

Для generate:
- ответ является строкой;
- после trim начинается с `flowchart LR` или `flowchart TB`;
- нет текста до и после Mermaid-кода.

Для edit:
- ответ является валидным JSON;
- присутствуют только поля `mermaid` и `message`;
- `mermaid` — непустая строка;
- `message` — непустая строка;
- `mermaid` начинается с `flowchart LR` или `flowchart TB`;
- `message` не содержит Mermaid-код, `flowchart`, `subgraph`, `classDef` или Markdown fence;
- message имеет разумный лимит длины;
- дополнительные поля запрещены.

6. ЗАПРЕЩЁННЫЕ КОНСТРУКЦИИ

Отклонить Mermaid, содержащий без учёта регистра:
- `<script`;
- `<iframe`;
- `<object`;
- `<embed`;
- `<foreignObject`;
- `<br`;
- `javascript:`;
- `click `;
- `href`;
- `%%{init`;
- внешние URL;
- Markdown fences ```.

7. СИНТАКСИС И РЕНДЕР

- использовать Mermaid parser той же версии, что и frontend;
- выполнять parse до рендера;
- рендерить с `securityLevel: "strict"`;
- использовать уникальный render id;
- не обновлять UI до успешного parse и render.

8. СТРУКТУРНЫЕ ПРОВЕРКИ

Проверить:
- первая строка — `flowchart LR` или `flowchart TB`;
- ID узлов уникальны;
- ID subgraph уникальны;
- стрелки не ссылаются на отсутствующие узлы;
- class назначается существующим узлам;
- style назначается существующим элементам;
- ✅ и ❌ находятся внутри текста узла;
- нет пустых узлов;
- нет оборванных стрелок;
- нет лишнего текста после Mermaid.

9. ЭВРИСТИКИ ЧИТАЕМОСТИ

Передавать в VALIDATION_ISSUES:
- больше 22 узлов;
- больше 5 узлов в одной очевидной горизонтальной цепочке;
- подпись узла длиннее 6 слов;
- подпись стрелки длиннее 3 слов;
- `flowchart LR` при количестве узлов больше 12;
- `direction LR` внутри subgraph с более чем 5 узлами;
- больше 5 крупных subgraph;
- большое количество обратных или межмодульных связей.

10. ПРОВЕРКА НАЛОЖЕНИЙ ПОСЛЕ РЕНДЕРА

После получения SVG:
- проверить, что bounding box текста помещается в родительский узел;
- проверить пересечение bounding box узлов одного уровня;
- при наложении добавить `LAYOUT_OVERLAP`;
- при чрезмерной ширине добавить `LAYOUT_TOO_WIDE`;
- при слишком плотном расположении добавить `LAYOUT_DENSE`.

11. ОДНА ПОПЫТКА РЕМОНТА

Если проверка не пройдена:
1. Вызвать repairMermaid.prompt.txt.
2. Передать CANDIDATE_MERMAID, PARSER_ERROR, VALIDATION_ISSUES и SOURCE_SPECIFICATION.
3. Повторить весь набор проверок.
4. Больше repair не вызывать.

12. АТОМАРНОЕ ОБНОВЛЕНИЕ UI

Только после полной успешной проверки одной операцией:
- сохранить previousMermaid;
- сохранить currentMermaid;
- перерисовать схему;
- добавить поле message в чат.

Mermaid-код в чат не выводить.

Если повторная проверка не прошла:
- оставить текущую схему без изменений;
- не менять previousMermaid;
- не показывать candidate Mermaid;
- показать короткое сообщение без технических деталей.

13. ОДИН АКТИВНЫЙ ЗАПРОС

Frontend:
- блокировать отправку;
- блокировать быстрые действия;
- блокировать добавление/удаление вложения;
- показывать состояние выполнения.

Backend:
- использовать session lock и requestId;
- не запускать второй запрос той же сессии;
- не применять запоздалый ответ;
- освобождать lock в finally.

14. БЫСТРЫЕ ДЕЙСТВИЯ

- «Разбить схему на смысловые блоки» → GROUP_SEMANTIC_BLOCKS;
- «Упростить схему» → SIMPLIFY;
- «Выделить основной путь» → HIGHLIGHT_MAIN_PATH.

Тип действия не определяется только сравнением текста кнопки.
