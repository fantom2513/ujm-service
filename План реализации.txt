ПЛАН РЕАЛИЗАЦИИ

Назначение документа

Этот план описывает, как последовательно создать рабочий сервис Copilot для построения Mermaid-схем. Сервис должен работать локально, быть переносимым и соответствовать ТЗ, Figma-макетам и утвержденному системному промпту.

Технические термины простыми словами

Frontend - часть сервиса, которую видит пользователь в браузере.
Backend - серверная часть, которая принимает файлы и ссылки, обращается к ИИ, хранит системные промпты и API-ключи.
API - набор адресов backend, к которым frontend обращается для выполнения действий.
Mermaid - текстовый язык описания схем, который затем превращается в визуальную диаграмму.
Рендеринг - превращение Mermaid-кода в видимую схему.
Валидация - проверка, что данные корректны и безопасны для обработки.
SessionStorage - временное хранилище браузера в пределах одной вкладки.
Промпт - инструкция для ИИ. Системный промпт задает обязательные правила работы модели.

1. Зафиксировать границы сервиса

Сначала нужно закрепить, что в продукт входит только две страницы:

1. Стартовая страница.
2. Страница результата.

Не нужно создавать регистрацию, авторизацию, личный кабинет, проекты, историю схем, постоянную базу данных и основную страницу продукта.

Главная страница продукта должна быть только внешним адресом, на который можно перейти после подтверждения в модальном окне. Сам адрес должен задаваться настройкой, а не быть жестко указанным в коде.

2. Подготовить основу проекта

Нужно создать переносимый локальный проект с двумя частями:

1. Frontend.
2. Backend.

Проект должен запускаться на другом компьютере после установки зависимостей и заполнения файла настроек. Реальные API-ключи в проект не добавляются.

Нужно подготовить:

- инструкцию запуска;
- пример файла настроек без секретов;
- описание подключения OpenAI;
- описание подключения Jira и Confluence;
- описание обработки файлов и записей;
- описание места хранения системных промптов;
- список известных ограничений.

3. Реализовать frontend по Figma

Frontend должен повторять состояния из Figma, а не придумывать новые экраны.

На стартовой странице нужно реализовать:

- выбор одного из трех источников;
- источник "Текстовый файл";
- источник "Запись встречи";
- источник "Ссылка на Jira или Confluence";
- поле дополнительных деталей;
- кнопку "Построить схему";
- loading-состояния для каждого источника;
- только утвержденные состояния ошибок.

При переключении источника данные предыдущего источника должны очищаться.

На странице результата нужно реализовать:

- область просмотра Mermaid-схемы;
- AI-чат;
- блок исходного контекста;
- блок дополнительных деталей, если они были введены;
- кнопку "Скачать схему";
- кнопку "Новая схема";
- кнопку "На главную";
- модальные окна подтверждения;
- dropdown скачивания;
- состояния чата из Figma.

Mermaid-код нельзя показывать как отдельный редактор.

4. Реализовать временное состояние в браузере

Так как постоянной базы данных нет, состояние нужно хранить только в текущей вкладке браузера.

После обновления страницы должны восстанавливаться:

- выбранный источник;
- введенная ссылка;
- дополнительные детали;
- метаданные уже обработанного файла или записи;
- построенный Mermaid-код;
- визуальное состояние схемы;
- масштаб и положение схемы;
- сообщения чата;
- страница результата, если схема уже построена.

Локальный файл нельзя автоматически восстановить после обновления, если браузер больше не дает к нему доступ. В таком случае пользователь должен прикрепить файл повторно.

5. Реализовать backend для приема данных

Backend должен принимать три вида источников:

1. Текстовый файл.
2. Запись встречи.
3. Ссылку на Jira или Confluence.

Для текстовых файлов backend должен:

- принять один файл;
- проверить размер до 10 МБ;
- проверить расширение;
- проверить фактический тип файла;
- извлечь текст из TXT, DOCX или PDF;
- удалить временный файл после обработки или ошибки.

PDF обрабатывается только при наличии доступного текста. Сканированные PDF без доступного текста не распознаются, не передаются в AI и показываются через существующее состояние неуспешной загрузки attachment-компонента.

Для записей backend должен:

- принять один файл;
- проверить размер до 100 МБ;
- проверить расширение;
- проверить фактический тип файла;
- для MP4 и WebM извлечь аудиодорожку;
- выполнить транскрибацию;
- удалить временный файл и временные данные после обработки или ошибки.

Для ссылок backend должен:

- проверить, что ссылка заполнена;
- проверить корректность URL;
- определить Jira или Confluence;
- получить содержимое через заранее настроенный серверный доступ;
- преобразовать содержимое в текст;
- передать текст в общий процесс генерации схемы.

Логин, пароль или API-токен у пользователя запрашивать нельзя.

6. Подготовить общий процесс генерации схемы

Для всех источников должен быть один общий процесс:

1. Получить нормализованный текст.
2. Отдельно получить дополнительные детали пользователя.
3. Передать данные в ИИ вместе с системным промптом на backend.
4. Получить название схемы и полный Mermaid-код.
5. Проверить Mermaid-код.
6. Если есть ошибка, выполнить одну автоматическую попытку исправления.
7. Повторно проверить Mermaid-код.
8. Если проверка успешна, вернуть результат на frontend.
9. Если проверка неуспешна, вернуть общую ошибку генерации.

Системный промпт нельзя менять, сокращать или отправлять на frontend.

7. Реализовать проверку Mermaid перед отображением

До отображения схема должна пройти проверку.

Проверка должна убедиться, что:

- код можно разобрать как Mermaid;
- первая строка соответствует ожидаемому формату flowchart LR;
- в коде нет пользовательского HTML;
- Mermaid запускается в безопасном режиме;
- SVG после рендера очищается от потенциально опасного содержимого;
- классы и стили не ссылаются на несуществующие элементы, если это возможно проверить автоматически;
- ошибки и успехи не ломают отображение схемы.

Если проверка не прошла, пользователь не должен увидеть техническую ошибку, Mermaid-код или stack trace.

8. Реализовать отображение схемы

Frontend должен отображать проверенную Mermaid-схему в отдельной области.

Нужно реализовать:

- автоматическое центрирование после первого построения;
- перемещение схемы мышью;
- изменение масштаба колесом мыши;
- кнопки "+" и "-";
- шаг изменения масштаба кнопками "+" и "-" 25%;
- минимальный масштаб 25%;
- максимальный масштаб 200%;

Состояние масштаба и положение схемы нужно сохранять в текущей вкладке.

9. Реализовать AI-чат для изменения схемы

Чат должен менять уже построенную схему, а не создавать отдельный редактор Mermaid.

При отправке сообщения backend должен получить:

- исходное нормализованное ТЗ;
- дополнительные детали;
- текущий Mermaid-код;
- сообщение пользователя;
- данные прикрепленного файла, если пользователь добавил файл к сообщению;
- системный промпт редактирования.

Backend должен вернуть:

- полный обновленный Mermaid-код;
- текстовый ответ для чата.

Обновлять схему можно только после успешной проверки нового Mermaid-кода. Если проверка не прошла, текущая схема должна остаться без изменений.

Пользователь может прикрепить к сообщению один файл размером до 10 МБ.

Поддерживаемые текстовые и табличные форматы:

- TXT;
- DOCX;
- PDF;
- XLS;
- XLSX;
- CSV.

Поддерживаемые форматы записей:

- MP3;
- M4A;
- MP4;
- WebM.

Изображения не поддерживаются.

PDF в чате обрабатываются только при наличии доступного текста. Сканированные PDF без доступного текста не распознаются.

Текстовый или табличный файл нужно извлечь и передать как дополнительный контекст текущего сообщения.

Аудиозапись или видео нужно расшифровать. Полученную транскрибацию нужно передать как дополнительный контекст текущего сообщения.

Файл в чате:

- не заменяет первоначальное ТЗ;
- не становится новым основным источником;
- обрабатывается вместе с текстом сообщения;
- временно хранится только во время обработки;
- удаляется после успешной обработки или ошибки.

Для файла в чате используются существующие состояния attachment-компонента:

- некорректный формат;
- превышение размера 10 МБ;
- ошибка загрузки.

Ошибка "Необходимо прикрепить файл" для чата не используется, потому что файл необязателен.

Одновременно должен выполняться только один AI-запрос. Пока идет генерация, отправка второго запроса, прикрепление файла и удаление прикрепленного файла блокируются.

10. Реализовать скачивание схемы

На странице результата нужно реализовать скачивание:

- PNG;
- SVG;
- PDF.

Скачивается только схема, без элементов интерфейса.

PNG должен иметь белый фон и хорошее разрешение.
SVG должен быть очищен от исполняемых скриптов и иметь корректный viewBox.
PDF должен не обрезать схему и выбирать ориентацию по пропорциям.

Имена файлов должны формироваться по шаблонам:

- ux_arch_YYYY-MM-DD_HH-mm.png
- ux_arch_YYYY-MM-DD_HH-mm.svg
- ux_arch_YYYY-MM-DD_HH-mm.pdf

11. Реализовать навигацию и очистку состояния

Кнопка "Новая схема" должна открывать модальное окно из Figma. После подтверждения нужно очистить текущую сессию, удалить временное состояние браузера и вернуть пользователя на стартовую страницу.

Кнопка "На главную" должна открывать отдельное модальное окно из Figma. После подтверждения нужно очистить текущую сессию, удалить временное состояние браузера и перейти на внешний адрес главной страницы продукта.

Системные предупреждения браузера при обновлении страницы, закрытии вкладки и использовании кнопки "Назад" не используются.

При обновлении страницы результат и текущее состояние должны восстанавливаться автоматически, насколько это возможно технически.

При закрытии вкладки данные текущей сессии удаляются без предупреждения.

При использовании браузерной кнопки "Назад" текущее состояние удалять нельзя.

12. Настроить безопасность

Нужно обеспечить:

- хранение API-ключей только на backend;
- хранение системных промптов только на backend;
- отсутствие секретов в frontend;
- проверку размера файлов на frontend и backend;
- проверку расширения и фактического типа файла;
- очистку названий файлов;
- запрет опасных путей и исполняемых файлов;
- ограничение времени обработки;
- безопасный режим Mermaid;
- очистку SVG;
- запрет рендера пользовательского HTML;
- отсутствие полного ТЗ, транскриптов и секретов в production-логах.

13. Настроить обработку ошибок

Frontend должен показывать только ошибки, которые есть в ТЗ и Figma.

Для текстового файла:

- "Необходимо прикрепить файл";
- "Некорректный формат файла";
- "Файл превышает 10 МБ".

Для записи встречи:

- "Необходимо прикрепить файл";
- "Некорректный формат файла";
- "Файл превышает 100 МБ".

Для ссылки:

- "Поле обязательно для заполнения";
- "Неверный формат ссылки";
- "Источник недоступен. Проверьте ссылку и права доступа".

Для общей ошибки генерации:

- "Схема не сформирована. Перезагрузите страницу или повторите попытку позже".

Для неуспешной передачи или обработки файла в attachment-компоненте:

- использовать существующее состояние ошибки attachment-компонента;
- не создавать отдельный экран;
- не добавлять новые пользовательские ошибки.

Технические причины должны сопоставляться с ближайшим пользовательским состоянием.

14. Проверить сервис перед передачей

Перед передачей разработчикам нужно проверить:

- запуск frontend и backend локально;
- отсутствие секретов в клиентском коде;
- работу трех источников;
- проверку размеров и форматов файлов;
- обработку ошибки недоступной ссылки;
- генерацию схемы через backend;
- проверку Mermaid перед показом;
- автоматическую попытку исправления Mermaid;
- восстановление состояния после обновления страницы;
- модальные окна "Новая схема" и "На главную";
- скачивание PNG, SVG и PDF;
- отсутствие постоянного сохранения пользовательских данных;
- соответствие интерфейса Figma-макетам.

15. Передать проект команде

Команде разработчиков нужно передать:

- исходный код проекта;
- README с запуском;
- пример файла настроек без секретов;
- список нужных внешних сервисов;
- описание системных промптов без публикации их на frontend;
- описание ограничений;
- список открытых вопросов из файла "Недостающие требования.txt".
