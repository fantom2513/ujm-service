## 1. Ложный отказ загрузки валидного PDF

**Баг (крит, скрин 1):** загрузка обычного PDF в источник "Текстовый файл" падала с общей "Ошибка загрузки файла", хотя файл был нормальным документом с текстом.

**Причина:** `backend-py/app/api/generate.py:84` (было) гейтил файл через `has_pdf_text_layer()` (`backend-py/app/services/files/extract.py`) — эвристику, ищущую операторы `BT`/`Tj`/`TJ` в сырых байтах PDF через regex по latin1. У подавляющего большинства реальных PDF (Word "Сохранить как PDF", печать в PDF и т.д.) content stream сжат `FlateDecode`, поэтому эти операторы лежат в бинарном блоке и не совпадают с regex — функция ложно возвращает `False` даже для PDF с полноценным текстовым слоем. Юнит-тесты не ловили это, т.к. использовали искусственный несжатый PDF-фрагмент.

Подтверждено экспериментально: собран синтетический PDF с реальным текстом внутри сжатого content stream (как делают настоящие генераторы) — `has_pdf_text_layer` возвращала `False`, а реальный экстрактор (`pypdf`, `backend-py/app/services/files/pdf.py`) корректно извлекал текст.

**Фикс:** убрали `has_pdf_text_layer()` целиком (мёртвый код после фикса, вместе с её тестами в `test_extract.py`). `/api/generate` теперь, как и `/api/chat` (`_read_attachment_context` в `chat.py`, тот же паттерн уже был там правильным), сначала реально парсит файл через `normalize_text_file()` → `parse_pdf`/`parse_docx`, и только если тот вернул `stub=True` (реально нечего извлечь — например, скан без текстового слоя) — отдаёт `attachment-error`. Раньше `/api/generate` для текстового файла не проверял `stub` вообще и просто генерировал схему из строки-заглушки — теперь генерация схемы из нечитаемого файла тоже блокируется явной ошибкой, а не тихо уезжает в LLM как мусорный текст.

**Файлы:** `backend-py/app/api/generate.py`, `backend-py/app/services/files/extract.py`, `backend-py/tests/services/files/test_extract.py`.

**Тесты:** `pytest tests/services/files/test_extract.py tests/api/test_generate_endpoint.py` — 19 passed; полный `pytest` — 221 passed, 69 skipped.

**Файлы:** `frontend/src/main.ts`.

**Уточнение (найдено при живом тестировании):** кнопка подтверждения внутри самой модалки (`#modal-confirm`, сценарий "home") тоже называлась "На главную" — пропустил её при первом фиксе, переименовал в "Назад" вместе с заголовочной кнопкой.

## 5. Растянутый PNG при экспорте

**Баг (крит, скрин):** скачанная PNG-картинка схемы выходит растянутой/перекошенной. Совпадает с открытым (неподтверждённым на момент записи) пунктом №19 из `docs/superpowers/specs/2026-08-28-frontend-figma-bugfixes-design.md` — там уже была ровно эта гипотеза, но не проверено, что реально отдаёт Mermaid.

**Причина:** `diagramSize()` (`frontend/src/utils/export.ts`) читала атрибуты `width`/`height` у корневого `<svg>`. Mermaid (дефолтный `useMaxWidth: true`) отдаёт `width="100%"` и вообще не ставит атрибут `height` — реальные пропорции схемы есть только в `viewBox`. `Number("100%")` → `NaN`, `Number(null)` → `0` — оба фолбэка через `||` всегда срабатывали на захардкоженные `SVG_WIDTH`/`SVG_HEIGHT` (980×520) независимо от реальной формы диаграммы. `downloadPng()` создаёт canvas с этими фиксированными размерами и растягивает на них изображение через `drawImage` — если реальное соотношение сторон схемы отличается от 980:520 (типичный случай для сложных флоучартов), картинка выходит перекошенной.

**Фикс:** `diagramSize()` теперь в первую очередь парсит `viewBox` (реальные width/height рендера), и только если его нет — падает на атрибуты `width`/`height`, и только в их отсутствие — на константы-заглушки (актуально только для собственного `fallbackSvg()`, у которого оба атрибута выставлены явно и совпадают с viewBox). Значения округляются (`Math.round`) — у Mermaid `viewBox` почти всегда дробный, и это же округление позже оказалось критичным для PDF-экспорта (см. пункт 6 — не округлённое, оно давало нецелый `/Width` в PDF и пустую картинку).

**Файлы:** `frontend/src/utils/export.ts` (`diagramSize()`).

**Тесты:** DOM-функций в export.ts тестами не покрыто (в репозитории вообще нет DOM-test harness для frontend, `jsdom` не установлен) — логика проверена вручную рассуждением + `npm run build`/`npm test` (97 passed) на отсутствие регрессий в остальном.

## 6. Реальный экспорт в PDF (растровый, вариант 1 из рассмотренных)

**Баг (крит, скрин):** пункт меню "PDF" не отдавал PDF. `downloadPdf()` (было, `frontend/src/utils/export.ts:97-107`) — осознанная MVP-заглушка: возвращала тот же blob, что и кнопка "SVG" (`type: "image/svg+xml"`, имя файла с расширением `.svg`), о чём прямо говорил комментарий в коде ("out of scope for this task"). Пользователь кликал "PDF", получал файл, который не открывается как PDF.

**Рассмотренные варианты** (см. предыдущую версию этого пункта): 1 — растровый PDF без новых зависимостей, 2 — векторный через библиотеку (`jsPDF`+`svg2pdf.js`/`pdf-lib`), 3 — серверный рендер (headless-браузер). Выбран **вариант 1** — дешевле и без новой зависимости через нексус; минус (растровый, не векторный — не даёт копируемый/ищущийся текст) принят как приемлемый компромисс для MVP.

**Реализация:**
- Вынес общий рендер диаграммы в canvas из `downloadPng()` в `renderDiagramToCanvas()` — используется теперь обоими экспортами, оба берут пропорции из уже исправленного `diagramSize()` (пункт 5).
- `downloadPdf()` рендерит тот же canvas в **JPEG** (не PNG) через `canvas.toBlob(..., "image/jpeg", 0.92)` — JPEG выбран специально: PDF-фильтр `/DCTDecode` — это как раз формат JPEG, поэтому байты JPEG можно вставить в PDF как есть, без перекодирования (тот же трюк, что используют библиотеки вида jsPDF).
- `buildPdfFromJpeg()` — ручная сборка минимального валидного одностраничного PDF: `Catalog → Pages → Page` с `/MediaBox`, размеченным в pt один-в-один с (неоверсэмпленными) размерами схемы из `diagramSize()`, `Contents`-стрим, растягивающий image XObject на всю страницу (`cm`/`Do`), сам XObject с `/Filter /DCTDecode` и сырыми байтами JPEG, и xref-таблица с точными byte-offset'ами каждого объекта.
- `exportDiagram()` в `main.ts` — `downloadPdf()` стала `async`, добавлен `await` на вызов (без него ошибка/задержка внутри неё не долетела бы до `catch`, а `exportState` показал бы "готово" раньше, чем PDF реально собрался).

**Проверка (первый заход):** функция сборки PDF воспроизведена в Node с валидным 1×1 JPEG и открыта через `pypdf` — распарсилась корректно: 1 страница, верный `MediaBox`, найден image XObject. `npm run build`/`npm test` (97 passed) — без регрессий в остальном.

**Баг найден живым тестированием: скачанный PDF открывался пустым белым листом.** Причина — `diagramSize()` (пункт 5) отдаёт **дробные** числа: реальный `viewBox` у Mermaid почти всегда нецелый (`"0 0 842.859375 391..."`), а `buildPdfFromJpeg()` подставляла эти дробные `width`/`height` прямо в `/Width`/`/Height` объекта-изображения — по спецификации PDF эти поля обязаны быть целыми. При этом `canvas.width = width * 2` браузер сам молча обрезает до целого (IDL-тип `unsigned long`), так что реальный JPEG кодировался с одним (целым) размером, а PDF заявлял другой (дробный) — рассинхрон, на который большинство PDF-вьюеров реагируют пустой отрисовкой картинки, а не ошибкой. Первый ручной тест это не поймал, потому что использовал круглые числа (100×60) вместо реалистичных дробных.

**Фикс:** `diagramSize()` теперь округляет (`Math.round`) размеры из `viewBox` (и из fallback-атрибутов `width`/`height`) сразу на входе — единая точка правды, дальше по цепочке (`canvas.width`, `/MediaBox`, `/Width`/`/Height` XObject'а) везде используются уже целые числа, рассинхрона больше нет. Перепроверено в Node на реалистичных дробных входных данных (843.859375×391.421875 → округляется до 843×391) — `pypdf` подтверждает: `/Width`/`/Height` образа — целые `NumberObject` (1686/782), `MediaBox` — целый.

**Файлы:** `frontend/src/utils/export.ts` (`diagramSize()`, `renderDiagramToCanvas()`, `canvasToBlob()`, `downloadPdf()`, `buildPdfFromJpeg()`), `frontend/src/main.ts` (`exportDiagram()`).

**Не в этой сессии:** вариант 2 (векторный PDF с копируемым текстом) — отдельная задача, если понадобится печать в высоком качестве или поиск текста внутри PDF.
