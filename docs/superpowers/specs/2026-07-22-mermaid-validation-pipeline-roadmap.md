# Дизайн: роадмап валидации Mermaid-пайплайна (превентивный технический долг)

Дата: 2026-07-22
Статус: зафиксировано на будущее — НЕ активный план реализации

## Контекст и цель

`Генерация схемы/system_prompts_mermaid_chat_v2/mermaidValidation.rules.txt`
описывает полноценный pipeline валидации генерации/редактирования
Mermaid-схем (14 разделов), который задумывался при исходном проектировании
модуля, но никогда не был реализован целиком. Текущий `validateMermaid()`
(`backend/src/services/mermaid/index.ts`) — это малая часть спеки: проверка
заголовка `flowchart` + 4 запрещённых паттерна.

Это НЕ реальные баги на проде (пользователи на это не жалуются) — это
превентивная защита на будущее. Цель этого документа — зафиксировать
разрыв между спекой и кодом и сгруппировать оставшуюся работу по
стоимости/ценности, чтобы к ней можно было вернуться осознанно, а не
переоткрывать её с нуля. Это НЕ веха с задачами на исполнение — активная
реализация не запланирована на момент написания.

## Метод

Полное сопоставление всех 14 разделов `mermaidValidation.rules.txt` с
фактическим кодом (`backend/src/services/mermaid/index.ts`,
`backend/src/services/openai/index.ts`, `backend/src/server/index.ts`,
`frontend/src/utils/export.ts`, `frontend/src/main.ts`), проверено по
исходникам, не по памяти/резюме.

## Состояние по разделам

| # | Раздел спеки | Статус | Что не хватает |
|---|---|---|---|
| 1 | Контракт запроса редактирования (requestId/sessionId) | ❌ отсутствует | `requestId`/`sessionId` нигде не заводятся и не передаются — ни на фронте, ни на бэке |
| 2 | Распознавание RESTORE_PREVIOUS | 🟡 почти готово | `UNDO_PHRASES`/`normalizeUndoMessage()` (`backend/src/server/index.ts:173-238`) корректно делают trim/lowercase/схлопывание пробелов/уборку пунктуации и меняют местами `currentMermaid`/`previousMermaid` — но не заменяют `ё`→`е`, как требует спека; фраза с `ё` не совпадёт с списком |
| 3 | Состояние версий в sessionStorage | ✅ готово | — |
| 4 | Вложение в чате | 🟡 частично | Размер/формат проверяются (`normalizeChatAttachment`), блокировка нового вложения во время активного запроса тоже есть (`frontend/src/main.ts`, `isChatLoading`-гейт на инпуте/кнопке удаления/отправке) — детали "не выполнять OCR"/"не передавать бинарник в промпт" не были явно верифицированы построчно |
| 5 | Проверка ответа модели (generate/edit) | 🟡 частично | JSON-схема (`CHAT_OUTPUT_SCHEMA`, `additionalProperties:false`, обязательные `mermaid`+`message`) структурно валидирует форму ответа — но нет проверки, что `message` не содержит Mermaid-код/`flowchart`/`subgraph`/`classDef`/Markdown fence, и нет лимита длины `message` |
| 6 | Запрещённые конструкции | ❌ почти отсутствует | `validateMermaid()` проверяет только `<script`, `</script`, `onerror=`, `onload=` — из требуемых спекой ~12 паттернов (`<iframe`, `<object`, `<embed`, `<foreignObject`, `<br`, `javascript:`, `click `, `href`, `%%{init`, внешние URL, Markdown fences) не проверяется ничего |
| 7 | Синтаксис и рендер | 🟡 частично | `securityLevel: "strict"` и render id уже есть (`frontend/src/utils/export.ts:21,29`), но render id на основе `Date.now()` не гарантирует уникальность при быстрых повторных рендерах; отдельного шага `mermaid.parse()` перед `mermaid.render()` нет — рендер сразу оборачивается в try/catch |
| 8 | Структурные проверки | ❌ отсутствуют | Нет проверки уникальности ID узлов/subgraph, оборванных стрелок, существования цели для `class`/`style`, размещения ✅/❌ строго внутри текста узла, пустых узлов, лишнего текста после Mermaid-кода |
| 9 | Эвристики читаемости | ❌ отсутствуют | Нет проверок количества узлов, длины цепочек, длины подписей, направления/размера subgraph и т.д. — ничего из раздела 9 не реализовано |
| 10 | Overlap-детекция после рендера (SVG bounding box) | ❌ отсутствует, и структурно сложнее остальных | Рендеринг Mermaid происходит **только на клиенте** через CDN-загружаемый `mermaid.esm.min.mjs` (`frontend/src/utils/export.ts`) — на backend вообще нет возможности рендерить SVG. Реализация этого пункта требует новой инфраструктуры (headless-браузер или серверный SVG-рендерер), а не просто функции валидации |
| 11 | Одна попытка ремонта | 🟡 частично | `chatEdit()` (`backend/src/services/openai/index.ts:66-83`) вызывает `buildRepairPrompt`/повторную валидацию ровно один раз при неудаче — но у `generateDiagram`/`handleGenerate` (`backend/src/server/index.ts:141-149`) repair-пути вообще нет: при неудачной валидации сразу 500 без повторной попытки |
| 12 | Атомарное обновление UI | ✅ готово | Присвоение состояния происходит только после полностью успешного ответа и в `buildDiagram`, и в `sendChat` — промежуточное/битое состояние никогда не коммитится |
| 13 | Один активный запрос на сессию | 🟡 частично | Фронтовая блокировка (`isChatLoading`) надёжно блокирует повторную отправку/quick actions/вложения — но backend session-lock + `requestId` + игнорирование "опоздавшего" ответа полностью отсутствуют |
| 14 | Quick-action → actionType не по тексту кнопки | 🟡 реальный разрыв | `quickActionType(label)` (`frontend/src/main.ts:425`) буквально сравнивает текст русской подписи кнопки (`if (label === "Разбить схему на смысловые блоки") return ...`) — ровно то, от чего явно предостерегает спека ("тип действия не определяется только сравнением текста кнопки") |

## Группировка по стоимости/ценности

### Tier 1 — дёшево, стоит сделать при первой возможности
- **#14** — заменить сравнение по тексту кнопки на стабильный `data-quick-action`/enum-ключ, не зависящий от отображаемой подписи.
- **#2** — добавить `ё`→`е` в `normalizeUndoMessage()`.
- **#6** — расширить список запрещённых паттернов в `validateMermaid()` до полного набора из раздела 6 (это добавление регулярных выражений, без изменения архитектуры).
- **#11** — добавить в `handleGenerate`/`generateDiagram` тот же repair-путь, что уже есть в `chatEdit`, для симметрии и единообразия обработки ошибок генерации.

### Tier 2 — средний объём, реальное укрепление корректности
- **#1 / #13** — ввести `requestId`/session-lock: генерировать `requestId` на фронте при старте запроса, хранить `activeRequestId` в session-state, backend отклоняет/игнорирует запросы не с последним `requestId` для той же сессии, снимать lock в `finally`. Защищает от гонки при быстрых повторных действиях пользователя.
- **#5** — добавить проверку содержимого и длины `message` (не содержит Mermaid-маркеры/fences, разумный лимит символов).
- **#8** — структурные проверки: уникальность ID узлов/subgraph, отсутствие ссылок на несуществующие узлы в стрелках/`class`/`style`, размещение ✅/❌ строго в тексте узла, отсутствие пустых узлов и лишнего текста после кода.

### Tier 3 — дорого/инфраструктурно, требует отдельного решения о старте
- **#9** — эвристики читаемости (лимиты на количество узлов, длину цепочек/подписей, размеры subgraph) — требуют подбора конкретных порогов на реальных данных/продуктовое решение, не чисто техническая задача.
- **#10** — overlap-детекция по SVG после рендера — требует **первого появления серверного рендеринга Mermaid** (headless-браузер в бэкенде или иной SVG-рендерер), это отдельная инфраструктурная инвестиция сопоставимая по объёму с целой новой подсистемой, не рядовая доработка.

## Что не входит в этот документ

- Приоритизация "когда именно" делать Tier 1/2/3 — сроки и порядок не зафиксированы, это решается отдельно, когда к этому вернутся.
- Детальный implementation-план (файлы, тесты, шаги) — не пишется сейчас, так как это roadmap-фиксация, а не активная веха. Полноценный `writing-plans`-документ имеет смысл писать непосредственно перед стартом работы над конкретным tier'ом.
- Раздел 10 (#9/#10 инфраструктурная часть) может потребовать отдельного архитектурного брейнсторминга перед планом — сюда входит выбор технологии серверного рендеринга (headless Chromium аналогично уже используемому в верификации тестов этого проекта, встроенный SVG-рендерер Mermaid для Node, и т.д.).
