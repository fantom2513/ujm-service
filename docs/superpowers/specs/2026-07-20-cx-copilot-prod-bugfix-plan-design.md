# Дизайн: план фикса прод-багов CX Copilot (TS-стек, до Python-миграции)

Дата: 2026-07-20
Статус: черновик на ревью

## Контекст и цель

Из багтрекера получена выжимка 18 замечаний по модулю генерации/просмотра
mermaid-схем и чату (🔴 критичные, 🟠 средние, 🔵 некритичные), подтверждённая
Figma-скринами с прод-инстанса (`cxcop.sogaz.ru`). Отдельно у проекта уже есть
согласованный дизайн миграции бэкенда на Python
([[2026-07-10-python-backend-infra-design]]) — там же зафиксирована главная
инфра-дыра "контекст диалога чата" как приоритет Фазы 2.

Цель этого плана — **не мигрировать сейчас**, а привести текущий Node/TS-сервис
в стабильное прод-состояние за счёт исправления багов из брифа, включая
лёгкий (не требующий БД/сессий) фикс потери контекста чата. Полноценная
серверная сессионная инфраструктура (Postgres/Redis, история) остаётся Фазой 2
Python-плана и этим документом не переопределяется.

## Зафиксированные решения

- **Стек:** остаёмся на текущем Node/TS backend + vanilla TS frontend. Python-
  миграция не блокируется и не ускоряется этим планом.
- **Контекст чата:** windowed-history (последние N сообщений) прокидывается из
  уже существующего клиентского состояния (`state.result.chat`,
  `sessionStorage`) в промпт на каждый запрос — без серверных сессий/БД.
  Полноценное управление контекстным окном (сжатие истории, лимиты) — вне
  скоупа, будет решаться после Python-миграции.
- **Usage-трекинг:** извлекать `usage` (prompt/completion/total tokens) из
  ответа vLLM и возвращать в ответе чата — задел для будущего контроля бюджета
  контекста, без реализации самой стратегии.
- **Системные промпты:** `.prompt.txt` файлы из `Генерация схемы/system_prompts_mermaid_chat_v2/`
  переезжают в `backend/prompts/`, читаются с диска при старте процесса и
  становятся единственным источником правды (сейчас в `backend/src/services/openai/prompts.ts`
  используются урезанные заглушки — комментарий в коде прямо называет их
  "Trimmed to key security + format rules"). Деплой — через существующий CI-раннер,
  без hot-reload/volume-монтирования.
- **Аналитика оценок (баг #7):** приёмника пока нет — делаем свой внутренний
  endpoint (без БД на этом этапе), с возможностью позже переключить на
  реальный приёмник.
- **Фронт/платформа CX Copilot (топология деплоя):** отдельный открытый вопрос,
  не блокирует этот план. Выносится в отдельную будущую спеку.

## Находки, объясняющие корневые причины багов

1. **Чат без памяти.** `sendChat` (`frontend/src/main.ts:857-928`) отправляет в
   `/api/chat` только `mermaidCode` (текущий) + `previousMermaidCode` (один шаг
   назад) + текст последнего сообщения. `buildChatPrompt`
   (`backend/src/services/openai/prompts.ts`) не принимает список сообщений —
   модель не видит историю диалога, хотя фронт её хранит и рендерит. Корень
   #15 и, вероятно, #9.

2. **Урезанные системные промпты.** `GENERATE_SYSTEM`/`EDIT_SYSTEM`/`REPAIR_SYSTEM`
   в `prompts.ts` — сильно сокращённые версии полных файлов
   `generateMermaid.prompt.txt` / `editMermaid.prompt.txt` / `repairMermaid.prompt.txt`.
   В рантайм-версии отсутствуют: правило "✅/❌ только внутри текста узла",
   стиль subgraph (`style ProcessA fill:#f9f9f9,...`), вся секция "КОМПОНОВКА
   СЛОЖНЫХ СХЕМ" (subgraph per процесс), и весь алгоритм действия
   `HIGHLIGHT_MAIN_PATH` (включая явный запрет `linkStyle` — "индексы связей
   нестабильны при последующем редактировании"). Корень #4, #5, #18, и
   ключевая часть #15: прод-скрин показывает, что выделение пути сейчас
   реализуется через раскраску рёбер, а не `classDef mainPath` на узлах, как
   требует полный промпт — отсюда нестабильность при повторной генерации.

3. **Ни в урезанной, ни в полной версии промпта нет стиля для decision-узлов**
   (`{"..."}`) — отсюда #3 (точки решения красные вместо `#ECECFF`). Нужно
   добавить новый `classDef`, которого не было в спеке никогда.

4. **Инверсия направления перекраски (#6)** — на фронте нет клиентской логики
   раскраски узлов (грепом подтверждено отсутствие в `frontend/src`), поведение
   целиком определяется LLM/FREEFORM-интерпретацией. Нужно точечное правило
   "источник цвета → цель" в FREEFORM-секции промпта.

5. **Кракозябры в именах файлов** (новая находка, не было в исходном брифе,
   видно на скринах вложений в чате) — кириллическое имя файла иногда
   отображается битым текстом (`Ð...docx`), но не всегда (на части скринов
   имя читается нормально). Похоже на проблему кодировки при передаче/декодировании
   multipart filename. Требует отдельного расследования при фиксе — где именно
   имя портится (загрузка на старте vs вложение в чате vs что-то в `chatAttachments`/`files`).

## Архитектурные изменения

### A. Контекст чата (Веха 0)

- Frontend (`main.ts`, `sendChat`): в FormData добавляется `history` — сериализованное
  окно последних N сообщений `state.result.chat` (роль + текст, без вложений).
- Backend (`server/index.ts` → `handleChat`, `services/openai/prompts.ts`):
  `ChatPromptOptions` получает `history: {role, text}[]`; `buildChatPrompt`
  добавляет `<CHAT_HISTORY>` блок в промпт.
- `infrastructure/llm/client.ts`: `_post` парсит `data.usage` из ответа vLLM
  (если присутствует) и возвращает вместе с `content`/`reasoningContent`;
  `chatEdit` прокидывает usage в `ChatEditResult` → в HTTP-ответ `/api/chat`.
  Фронт пока не обязан её показывать — просто прокидывается как задел.

### B. Синхронизация промптов (Веха 2)

- Переносим 4 файла `.prompt.txt` в `backend/prompts/` (генерация, эдит, репаир,
  правила валидации — свериться, используется ли `mermaidValidation.rules.txt`).
- `prompts.ts`: заменить константы `GENERATE_SYSTEM`/`EDIT_SYSTEM`/`REPAIR_SYSTEM`
  на чтение файлов при старте модуля (`readFileSync`, синхронно, как уже
  делает `config/index.ts` для `.env`).
- Добавить в `generateMermaid.prompt.txt`/`editMermaid.prompt.txt` секцию про
  `classDef decision` (`#ECECFF`/`#9370DB`) и `decisionNegative`
  (`#FFCDD2`/`#C62828`), плюс правило направления перекраски для FREEFORM.
- Docker/CI: убедиться, что `backend/prompts/` попадает в образ (Dockerfile,
  `.dockerignore`).

## Тестирование

- Веха 0: unit-тест на `buildChatPrompt` (история попадает в промпт, окно
  ограничено N сообщениями), unit-тест на парсинг `usage` в `client.ts`.
- Веха 1: regression-тест на каждый баг (навигация назад на result, имя файла
  в чате, кодировка кириллических имён, PNG-экспорт, ошибка при потере файла
  на старте).
- Веха 2: regression на синхронизацию промптов — снапшот-тест, что
  `prompts.ts` больше не содержит захардкоженных урезанных констант; e2e/интеграционный
  тест на HIGHLIGHT_MAIN_PATH (класс `mainPath` на узлах, не `linkStyle`);
  тест на `classDef decision`; z-index модалки, скролл вложений — frontend
  unit/e2e; авто-размер бабла — визуальный/snapshot.
- Веха 3: regression на каждый баг, включая новый endpoint аналитики.

## Общие требования (сквозные, из исходного брифа)

- Не ломать поведение вне описанных багов, не трогать код вне зоны бага.
- Минимум один regression-тест на пункт.
- Цвета/стили (#ECECFF, #9370DB, #FFCDD2, #C62828, rgba(21,33,73,0.6),
  #f9f9f9/#ddd) выносятся в общие константы/токены (frontend styles + mermaid
  classDef), а не хардкодятся по месту.
- После каждой вехи — краткое summary изменённых файлов и добавленных/обновлённых тестов.
