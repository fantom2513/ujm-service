# Дизайн: Python-бэкенд нового поколения для Mermaid Copilot

Дата: 2026-07-10
Статус: черновик на ревью

## Контекст и цель

Текущий backend — Node 24 / TypeScript (нативный type-stripping), ~15 файлов
(`backend/src`). Он production-ready (Docker + GitLab CI), но команда живёт на
Python/Go и не будет поддерживать TS долгосрочно. Отдельно: сервис сейчас не
имеет инфраструктурного слоя (нет БД, нет сессий, нет истории, чат stateless по
диалогу — модель не видит прошлые реплики, юзер «пишет в пустоту»).

Цель: переписать backend на **Python + FastAPI**, сохранив контракт `/api/*`
(фронт не трогаем), и заложить инфра-слой: контекст диалога → сессии → история →
кэш → заготовка авторизации.

## Зафиксированные решения

- **Стек:** Python + FastAPI (async).
- **Стратегия:** сборка нового бэка **поэтапно** (фаза за фазой, с проверкой
  каждой), выкат — **единым мажорным патчем** после тестирования текущей
  TS-версии. Параллельного strangler'а в проде нет — один cutover.
- **Фронт не трогаем** — тот же контракт `/api/*`
  (`/health`, `/config`, `/generate`, `/chat`).
- **Хранилище:** Postgres **per-product** (свой контейнер/БД этого сервиса:
  пользователи, сессии, история, схемы) + Redis (кэш, горячие сессии, кэш
  LLM-ответов, локи).
- **Инфра-репо:** общие stateful-сервисы (Redis, RabbitMQ, авторизация) и сеть
  `cx_net` живут в отдельном инфраструктурном репо платформы `cx_copilot`.
  Продукт `ujm-service` — тонкий: определяет только свои app-контейнеры + свой
  Postgres, а Redis/RabbitMQ/auth референсит как внешние.
- **Очередь:** RabbitMQ — **отложено**, пока не запускаем. Тяжёлых фоновых задач
  в ближайших фазах нет (транскрибация — заглушка). Вводим RabbitMQ + воркер
  только когда появится реальный STT. Redis как брокер НЕ используется в любом
  случае — только кэш/сессии/локи.
- **Многопользовательский режим:** несколько юзеров и, потенциально, несколько
  инстансов бэка. Сессии — в общем сторе (Redis + Postgres), не в памяти
  процесса.
- **Авторизация:** только заготовка (pluggable middleware, identity из заголовка
  gateway, привязка к `user_id`; своего логина нет).

## Архитектура

Новый сервис `backend-py` (FastAPI, async). Контейнер в сети `cx_net`, без
публичных портов, за reverse-proxy. В ближайших фазах продукт добавляет только
**свой Postgres**; Redis — из общего инфра-репо.

Инфра-компоненты по назначению:

- **Postgres (per-product, в этом репо)** — долговечное: пользователи, сессии,
  история диалога, версии схем. Свой контейнер `ux-architecture-postgres` +
  named volume, только внутри `cx_net`.
- **Redis (общий, инфра-репо)** — кэш LLM-ответов, горячие снапшоты сессий
  (TTL), распределённые локи. Подключение — напрямую из процесса через пул
  `redis.asyncio` по внешнему хосту инфра-репо, свой **логический DB-номер** +
  префикс ключей `uxarch:`. Прослойки-воркера перед Redis нет.
- **RabbitMQ + воркер (общий, инфра-репо)** — отложено (см. ниже). Свой vhost
  `/uxarch` при вводе.
- **Auth (общий, инфра-репо)** — gateway ставит identity-заголовок; продукт
  только его читает.

Слои (чистая архитектура):

- `api/` — роутеры + Pydantic-схемы (контракт /api).
- `domain/` — нормализация источников, mermaid-валидация, промпт-логика.
- `infrastructure/llm/` — порт LLM-клиента: retry, fallback по `response_format`
  (`json_schema` → `json_object` → `none`), insecure-TLS. Переносим поведение из
  TS 1:1.
- `infrastructure/store/` — репозитории Postgres + Redis-кэш за абстракцией
  `Cache`.
- `services/files|links|recordings/` — парсеры и заглушки.

## Дыра №1 — контекст диалога (ядро)

Серверная сессия. На `POST /generate` бэк создаёт сессию, кладёт нормализованный
источник + первую схему, ставит **httpOnly-cookie `session_id`** (браузер шлёт
автоматически → фронт не трогаем).

На `POST /chat` бэк:

1. по `session_id` поднимает транскрипт диалога + текущую схему + исходный
   контекст (Redis горячее / Postgres fallback);
2. строит промпт с **оконной историей** (последние N реплик) — модель видит
   предыдущие сообщения;
3. вызывает LLM, валидирует/чинит mermaid;
4. **персистит** новое сообщение + версию схемы;
5. возвращает ответ.

Закрывает **контекст чата + сессии + историю** одним куском.

> Открытый вопрос: серверная сессия через httpOnly-cookie (фронт не трогаем) —
> рекомендация. Альтернатива: явный `session_id` в теле запроса + правки фронта,
> что сразу открывает историю-UI. Уточнить на ревью.

## Модель данных (Postgres)

- `sessions(id, user_id?, source_type, source_text, additional_details,
  created_at, expires_at)`
- `messages(id, session_id, role, content, action_type, attachment_meta,
  created_at)` — транскрипт.
- `diagram_versions(id, session_id, mermaid_code, title, created_at)` — история
  схем + undo (заменяет `previousMermaid`).

Redis:

- `sess:{id}` — горячий снапшот транскрипта/схемы (TTL).
- `llmcache:{hash}` — кэш ответов LLM по хэшу промпта (детерминизм + экономия).

## Многопользовательские сессии и масштабирование

Пользователей несколько, бэк может работать в нескольких инстансах. Значит:

- **Сессия = `(user_id, session_id)`** — живёт в Redis (горячий снапшот, TTL) с
  персистом в Postgres. Любой инстанс поднимает ту же сессию → sticky-сессии на
  балансировщике не нужны.
- **`user_id`** приходит из заготовки auth (заголовок gateway). Сессии и история
  сразу привязаны к пользователю — изоляция между юзерами из коробки. Без
  заголовка — анонимная сессия по cookie.
- **Лок «один AI-запрос за раз»** (требование ТЗ) — распределённый **Redis-лок
  по `session_id`**, работает и при нескольких инстансах, а не только в пределах
  одного процесса.
- **TTL/expiry** сессий — per-user в Redis; долговечная история в Postgres своим
  TTL не ограничена.

## Заготовка авторизации

Pluggable `auth_dependency`: читает identity из заголовка/JWT gateway
(напр. `X-User-Id` / `Authorization`), кладёт `user_id` в request-scope,
привязывает сессии/историю к нему. Нет заголовка → анонимная сессия. Реальный
провайдер подключается позже сменой одной зависимости.

## Кэш

Абстракция `Cache` (get/set/ttl), реализация — Redis. Применения: кэш
LLM-ответов по хэшу промпта, горячие сессии, счётчики rate-limit. Подменяемо на
in-memory для локалки.

## Остаётся заглушкой / вне первого cutover

- **Транскрибация** — заглушка (модели нет), интерфейс `recordings.transcribe()`
  готов под Whisper.
- **Jira/Confluence** — реальный коннектор (доступ есть), текст-промпт
  финализируется отдельно.
- **XLS/XLSX** — закрываем сразу (`openpyxl`).
- **История-UI на фронте** — требует правок фронта → поздняя фаза, не в первом
  cutover.

## Деплой: инфра-репо + тонкий продукт

Общие stateful-сервисы выносятся в отдельный **инфраструктурный репо** платформы
`cx_copilot`. Границы владения:

- **Инфра-репо владеет:** сетью `cx_net` (создаёт её → у продуктов
  `external: true`), Redis, RabbitMQ, сервисом авторизации/gateway, их конфигом,
  секретами, бэкапами, версиями.
- **Продукт `ujm-service` владеет:** только своими app-контейнерами
  (`ux-architecture-backend/frontend`) и **своим Postgres**. Redis/RabbitMQ/auth
  референсит как внешние через `cx_net`.

**Контракт изоляции (чтобы общие сервисы не давали коллизий между продуктами):**

- **Redis** — свой логический DB-номер (`redis://cx-redis:6379/2`) + префикс
  ключей `uxarch:`.
- **RabbitMQ** — свой vhost `/uxarch` + отдельный юзер (при вводе, Фаза 6).
- **Postgres** — per-product, шарить между продуктами нельзя (свой блочный
  радиус, свои миграции).
- **Auth** — продукт только читает identity-заголовок общего gateway; своего
  логина/хранения паролей нет.
- **Версионирование контракта** — хостнеймы/порты/vhost/DB-номера стабильны,
  меняются только по согласованию (изменение в инфре ломает все продукты).

**Операционка инфра-репо:** local-dev профиль (поднять инфру локально, иначе
продукт в изоляции не запустить) и порядок старта (инфра первой — создаёт сеть).

## Дорожная карта (фазы = приоритет)

- **Фаза 0** — каркас FastAPI + Docker + Postgres/Redis + паритет
  `/health`, `/config`, CI.
- **Фаза 1** — LLM-слой + `/generate` (паритет с TS: retry/TLS/fallback).
- **Фаза 2** — **сессии + контекст чата + история** (`/chat` с диалогом) ←
  главный приоритет.
- **Фаза 3** — кэш (LLM-cache, горячие сессии) + заготовка auth.
- **Фаза 4** — парсеры (XLSX) + реальный Jira/Confluence-коннектор; интерфейс
  `recordings.transcribe()` как заглушка, готовая к подключению.
- **Фаза 5** — примирение спек-дрейфа mermaid-валидации, прод-логи без
  пользовательских данных, финальный e2e + cutover.
- **Фаза 6 (отложено)** — RabbitMQ + воркер-контейнер + реальная транскрибация
  (Whisper) как фоновая задача. Вводится, когда будет STT-модель и готовность
  запускать RabbitMQ.
